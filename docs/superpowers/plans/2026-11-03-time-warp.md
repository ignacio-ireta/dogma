# Time-warp: a personal course calendar (I-30)

**Goal:** the learner can move the course calendar by whole weeks, so a break or a busy stretch
never leaves the calendar ahead of the work. Three actions, in the CLI and in the web app:

1. **Sync** (the default warp): this week becomes the week of the furthest exercise the learner
   has run.
2. **Manual warp:** this week becomes week N, or the calendar moves N weeks ahead or back, or goes
   back to the authored dates.
3. **Course reset:** back up, clear all progress, set workspace files aside, and make this week
   week 1. A separate, typed-confirmation action.

**Spec:** ADR-0019, ARCHITECTURE §2 (calendar), §4.4 (planner, Interview sessions, missed days),
§9 of ENGINEERING_STANDARDS (data and migrations). The no-debt rule (ADR-0013) holds: no wording
about being behind, late or missing days, and no counts of missed time.

## Decisions

- **The authored calendar stays authored.** `curriculum/paths/core.yaml` is never rewritten. The
  learner's shift is learner state in SQLite: one integer, `offset_weeks`.
- **Shift arithmetic.** With `offset_weeks = k`, every `starts`, plus the path's `start` and `end`,
  moves by `7·k` days. Positive `k` moves the calendar later (more time); negative moves it
  earlier. Weekdays never change, so weeks stay Monday-based.
- **"This week becomes week N"** means `k = (today − authored_starts(N)).days // 7` (floor
  division), with `N` clamped to `1..len(weeks)` and `today = sessions.local_day(now)`. Example:
  on Tue 3 Nov 2026, week 1 (authored Mon 26 Oct) gives `k = 8 // 7 = 1`, so week 1 runs Mon 2 Nov
  to Sun 8 Nov and the course ends Sun 7 Feb 2027.
- **Sync anchor = the furthest core-path week among the exercises the learner has run.** Every
  recorded attempt counts (`run` or `submit`). Map `problem_id` → topic id → its week in the core
  path. Problems whose topic is not on the core path (tier B, `sys`) are ignored. No attempts → week
  1. "Furthest", not "most recent", so a timed re-solve or familiar practice of an older problem
  never pulls the calendar back. Return the problem id that set the anchor, for display.
- **Ahead / back:** target week = calendar week today ± N, clamped to `1..len(weeks)`, then the
  "this week becomes week N" formula. "Calendar week today" is `path.current_week` on the shifted
  path (week 1 before the start, the last week after the end).
- **Original:** `k = 0`.
- **What follows the shifted calendar:** the planner's `path_week` (weekly Interview sessions from
  week 3, the interview-only final week, the per-week interview count), `dogma path`, `dogma
  progress`, `GET /progress` (current week, week starts, course start and end) and the web pages
  that show them.
- **What does not move:** FSRS card due dates and timed re-solve due dates. They measure memory
  over real time; shifting them would make FSRS overrate retention after a break. Overdue reviews
  are already capped per day and spread out (ARCHITECTURE §4.4). Topic order never depended on
  the date.
- **Sessions already planned** keep their kind. A warp affects sessions planned after it.
- **Recording off** (`DOGMA_RECORD_ATTEMPTS=false`): reading the calendar and previews work;
  applying a warp or a reset is refused with `CALENDAR_RECORDING_OFF`, like mocks.
- **Wording.** Say "move the calendar", "this week becomes week N", "your furthest exercise is in
  week N". Never "behind", "late", "missed", "overdue weeks" or a count of days.

## Data

New table `calendar_warp`, one forward-only Alembic migration (down_revision `b8c9d0e1f2a3`, the
head after I-26):

| column | type | notes |
|---|---|---|
| `id` | Integer PK, autoincrement | the newest row is the latest warp |
| `created_at` | UtcDateTime | |
| `kind` | String(16), CHECK in `sync, to_week, ahead, back, original, course_reset` | |
| `offset_weeks` | Integer | the offset in force after this warp |
| `previous_offset_weeks` | Integer | |
| `week_before` | Integer, nullable | calendar week today before the warp |
| `week_after` | Integer, nullable | calendar week today after the warp |

The offset in force is the newest row's `offset_weeks`, or 0 with no rows. Register the model in
`src/dogma/db/migrations/env.py` like the others. `dogma backup` picks the table up through
`Base.metadata`; check it does.

## Domain module: `src/dogma/learning/calendar.py`

Pure helpers plus thin DB functions. Suggested surface (adjust names to the codebase style):

```python
def shift_path(core: CorePath, offset_weeks: int) -> CorePath            # pure
def offset_for_week(core: CorePath, week: int, today: date) -> int       # pure, clamps week
def load_calendar(settings: Settings) -> CorePath                        # authored path + offset
def current_offset(settings: Settings) -> int
def anchor(settings: Settings, core: CorePath) -> Anchor                 # week, problem_id | None
def status(settings: Settings, *, now: datetime) -> CalendarStatus       # offset, current week,
                                                                         # anchor, start, end, last warp
def preview(settings, request: WarpRequest, *, now) -> WarpPreview      # never writes
def apply(settings, request: WarpRequest, *, now) -> WarpPreview        # writes one row if changed
def reset_course(settings, *, now) -> ResetResult
```

`WarpRequest` is a kind plus `week` (to_week) or `weeks` (ahead/back, ≥ 1). `WarpPreview` holds
`kind`, `changed`, and a before and an after point: `offset_weeks`, `current_week`, the date the
current week starts, the start of week 3 (first weekly mock), the start of the last week (the
interview week) and the end date. `apply` with no change writes nothing and says so.

Switch every date-dependent reader to `load_calendar`: `learning/sessions.py::_load_core`,
`cli/progress.py`, `cli/path_view.py` (I-30a) and `api/services/learning.py` (I-30b).
`content/validate.py` keeps loading the authored file.

## Course reset

`reset_course(settings, *, now)`:

1. Refuse when recording is off.
2. `write_backup(settings, now=now)` (JSON export and DB snapshot). If it fails, stop: nothing is
   cleared.
3. In one transaction, delete every row of every table in `Base.metadata` except `calendar_warp`,
   children before parents (`reversed(sorted_tables)`). Then insert a `course_reset` warp row that
   makes this week week 1. List the cleared tables in the handoff.
4. After the commit, move every file under `settings.workspace_dir` into
   `var/workspace-history/reset-<UTC stamp>/`, keeping relative paths (follow
   `content/resolve.py::set_aside_workspace`). A failure here is reported, not raised: the DB is
   already reset and the backup exists.
5. Return the backup and snapshot paths, rows cleared per table, files set aside, and the new
   week-1 start date.

Run directories, the corpus, content and the catalog are untouched. Restoring is a file copy of the
snapshot over `var/dogma.db` with the server stopped; say so in the CLI output and the docs.

## I-30a: backend and CLI

**Owns:** `src/dogma/learning/calendar.py`, `src/dogma/db/calendar_models.py`, the new migration,
`src/dogma/db/migrations/env.py` (one import), `src/dogma/core/errors.py` (new codes only),
`src/dogma/learning/sessions.py` (`_load_core` only), `src/dogma/cli/progress.py`,
`src/dogma/cli/path_view.py`, `src/dogma/cli/warp_cmd.py`, `src/dogma/cli/main.py` (registration
only), and tests under `tests/unit/learning/`, `tests/unit/db/`, `tests/unit/cli/`.

CLI:

```
dogma warp [--to-week N | --ahead N | --back N | --original] [--dry-run] [--yes]
dogma course reset [--yes]
```

- No option means sync. The options are mutually exclusive (usage error otherwise).
- Print the before → after lines: "This week: week 2 → week 1", "Weekly mocks from: Mon 09 Nov →
  Mon 16 Nov", "Interview week: Mon 25 Jan → Mon 01 Feb", "Course ends: Sun 31 Jan 2027 → Sun 07
  Feb 2027". For sync, first say what set the target: "Your furthest exercise is in week 3
  (cml/gradient-descent/p01)." or "You haven't run an exercise yet, so this week becomes week 1."
- Then ask "Move the calendar? [y/N]" unless `--yes`. `--dry-run` prints and stops.
- No change: "This week is already week N. Nothing changed." Exit 0.
- `dogma path` and `dogma progress` show the shifted dates. When the offset is not 0, `dogma path`
  adds one line: "Dates moved N weeks later by time-warp. `dogma warp --original` restores them."
  (or "earlier").
- `dogma course reset` explains what it keeps and clears, then asks the learner to type `reset`
  (anything else cancels) unless `--yes`. It prints the backup path, the snapshot path and how to
  restore.

**Accept:** `make check` passes, plus tests for: the offset formula on every weekday and across the
year boundary; clamping; sync with no attempts, with only `run` attempts, with a re-solve of an older
problem (anchor does not drop), with a non-core problem (ignored); ahead/back clamping; original;
no-change applies write nothing; the planner's Interview sessions and the final interview week
follow a warp; the migration upgrades a fixture DB from `b8c9d0e1f2a3`; backup includes
`calendar_warp`; reset clears every other table, keeps the warp log, sets workspace files aside,
refuses with recording off, and clears nothing when the backup fails; CLI dry-run, `--yes`,
declining, conflicting flags, and the typed reset confirmation.

## I-30b: HTTP API and web

**Owns:** `src/dogma/api/routers/calendar.py`, `src/dogma/api/schemas/calendar.py`,
`src/dogma/api/services/calendar.py`, `src/dogma/api/app.py` (router registration only),
`src/dogma/api/errors.py` (status mapping only), `src/dogma/api/services/learning.py`
(`load_calendar` only), `web/src/api/{openapi.json,schema.d.ts,calendar.ts}`,
`web/src/pages/ProgressPage.tsx`, `web/src/pages/progress/`, `web/src/pages/TodayPage.tsx` and
`web/src/pages/today/` (the one-line offer), their tests, and `web/tests/e2e/calendar.spec.mjs`.

API (under `/api/v1`):

- `GET /calendar` → offset, current week (or null), anchor week and problem id, start, end, the
  weeks (number, starts, theme), and the last warp (kind, created_at) or null.
- `POST /calendar/warp` {kind, week?, weeks?, dry_run=false} → {applied, changed, before, after}.
  Bad combinations are 422. Recording off is 409 `CALENDAR_RECORDING_OFF`.
- `POST /course/reset` {confirm: "reset"} (a literal; anything else is 422) → the reset result.
- `GET /progress` uses the shifted calendar.

Web:

- **Progress page, Calendar section:** "This week is week X of 14 · the course ends <date>" and
  "Your furthest exercise is in week Y". Buttons: "Match my exercises (week Y)" (disabled when
  X = Y), "Go to week [1–14]", and "Back to the original dates" (only when the offset is not 0).
  Each opens a preview (a `dry_run` call) with the before → after lines, then Move / Cancel. After a
  move, refresh calendar, progress and today data.
- **Progress page, Start over section** at the bottom: what is kept and cleared, a button that opens
  a dialog where the learner types `reset`. Show the backup path afterwards.
- **Today page:** one neutral line, only when the calendar week is at least 2 weeks past the anchor
  (a real break, not a normal Monday): "Your furthest exercise is in week Y. Move the calendar so
  this week is week Y?" linking to the Progress page's Calendar section. No day counts.
- Regenerate the API types with `pnpm gen:api`.

**Accept:** `make test-all` passes, plus API route tests for every kind, dry run, no change,
recording off and the reset confirmation; web unit tests for the preview flow, the reset dialog and
the Today line's threshold; one Playwright test that previews and applies a sync and checks the
Progress page's week; no horizontal scroll at 390px.
