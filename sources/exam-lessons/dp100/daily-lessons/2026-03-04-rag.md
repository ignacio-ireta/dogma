## 📊 CONCEPT MAP: RAG as a SYSTEM (15 min)

### THE FOUR-WORD DEFINITION

> **RAG = Retrieval-Augmented Generation**
> Give the LLM REAL facts from YOUR data at query time, so it doesn't hallucinate.

Without RAG: LLM answers from training data (stale, possibly wrong)
With RAG: LLM answers from *your* retrieved documents (current, grounded, auditable)

---

### THE FULL RAG PIPELINE — 6 Stages

```
  DATA SOURCES             INDEXING PIPELINE              QUERY PIPELINE
  ─────────────            ─────────────────              ──────────────
  Azure Blob Storage   →   1. INGEST          
  SharePoint               2. CHUNK          →   User Query
  OneLake                  3. EMBED          →   3. EMBED query
  SQL / CosmosDB           4. INDEX          →   4. RETRIEVE (search)
  Custom sources                              →   5. AUGMENT (build prompt)
                                              →   6. GENERATE (LLM response)
```

Each stage is a design decision. The exam tests EVERY stage.

### STAGE 1 — INGEST 📥

**What it means:** Get your source documents into the pipeline.

**Supported data sources (Azure AI Search):**
| Source | Notes |
|--------|-------|
| Azure Blob Storage | Most common — PDFs, DOCX, TXT, HTML, JSON |
| Azure Data Lake Storage Gen2 (OneLake) | For Fabric-integrated pipelines |
| SharePoint Online | Requires connector + managed identity |
| Azure SQL Database | Structured data — usually not for RAG |
| Azure Cosmos DB for NoSQL | JSON documents |

**Key concept:** Azure AI Search **Indexers** automate the ingest → chunk → embed → index pipeline. When a document is added to Blob Storage, the indexer detects the change and processes it automatically.

**⚠️ EXAM TRAP:** You need both an **Index** (stores the data) and an **Indexer** (runs the pipeline). They are separate resources!

---

### STAGE 2 — CHUNK ✂️

**Why chunk?** LLMs have token limits. A 50-page PDF won't fit in a prompt. You split it into smaller pieces, each of which can be independently retrieved.

**The Three Main Chunking Strategies:**

#### Strategy 1: Fixed-Size / Token-Based Chunking
```
Split every N tokens (e.g., 512 tokens)
With overlap: last 50 tokens of chunk N become start of chunk N+1
```
- ✅ Simple, fast, predictable
- ❌ Can split mid-sentence, losing context
- **Best for:** Homogeneous text (e.g., long articles, logs)
- **Azure param:** `chunk_size`, `chunk_overlap`

#### Strategy 2: Sentence / Paragraph Chunking
```
Split at natural boundaries: sentence endings, paragraph breaks, headings
```
- ✅ Preserves semantic meaning
- ❌ Variable chunk sizes = inconsistent retrieval
- **Best for:** Structured documents (reports, manuals)

#### Strategy 3: Semantic Chunking
```
Use an LLM or embedding model to detect topic shifts and split there
```
- ✅ Best quality — chunks are semantically coherent
- ❌ Expensive (requires LLM call per chunk boundary)
- **Best for:** Complex, multi-topic documents

**⚠️ EXAM TRAP:** "Which chunking strategy minimizes context loss while fitting within token limits?"
→ Answer: **Fixed-size with overlap** (the overlap preserves cross-chunk context)

**Chunk size trade-offs:**
| Smaller chunks | Larger chunks |
|---------------|---------------|
| More precise retrieval | More context per chunk |
| More chunks = bigger index | Fewer chunks = smaller index |
| Risk: missing context | Risk: irrelevant content dilutes the answer |

---

### STAGE 3 — EMBED 🔢

**What it means:** Convert text chunks into **vector embeddings** — dense numerical representations that capture semantic meaning.

**Why?** Vectors let you search by *meaning*, not just keywords.

**Azure Embedding Models (know these for the exam):**

| Model | Provider | Dimensions | Notes |
|-------|----------|------------|-------|
| `text-embedding-3-small` | Azure OpenAI | 1536 | Fast, cheap, default choice |
| `text-embedding-3-large` | Azure OpenAI | 3072 | Higher quality, more expensive |
| `text-embedding-ada-002` | Azure OpenAI | 1536 | Older, still common in exam questions |
| Cohere Embed v3 | Cohere (via Model Catalog) | 1024 | Good multilingual support |

**Where to deploy embeddings:**
- Azure OpenAI Service → deploy as embedding model deployment
- Microsoft Foundry Model Catalog → deploy to Azure AI Services endpoint

**⚠️ EXAM TRAP:** The embedding model used to **index** documents MUST be the same model used to **embed the query** at search time. Different models → incompatible vector spaces → garbage results.

---

### STAGE 4 — INDEX 📚

**What it means:** Store the vectors (and the original text) in a searchable vector store.

**Azure AI Search as Vector Store:**

Azure AI Search is the PRIMARY vector store for DP-100 / Domain 4. Know this architecture:

```
Azure AI Search Index
├── Fields:
│   ├── id (string, key)
│   ├── content (string — the original chunk text)
│   ├── content_vector (Collection(Edm.Single) — the embedding)
│   ├── metadata (string — source file, page number, etc.)
│   └── category / tags (string — for filtering)
└── Algorithms:
    ├── HNSW (Hierarchical Navigable Small World) — default, fast ANN search
    └── ExhaustiveKNN — brute force, 100% accuracy, slower
```

**Search types in Azure AI Search:**

| Type | How it works | Best for |
|------|-------------|----------|
| **Keyword search** | BM25 text matching | Exact terms, IDs, codes |
| **Vector search** | Cosine similarity on embeddings | Semantic meaning, paraphrases |
| **Hybrid search** | BM25 + vector, fused with RRF | **Best overall — exam default answer** |
| **Semantic ranker** | Cross-encoder re-ranks top results | When precision matters most |

**⚠️ EXAM TRAP:** "Which search type gives the best results for a customer support chatbot?"
→ **Hybrid search** (combines keyword precision + semantic understanding)

**Reciprocal Rank Fusion (RRF):** Azure AI Search's algorithm for merging keyword and vector results. You don't need to know the math — just know that RRF is how hybrid search combines the two rankings.

**Creating an index in Azure AI Search (Python SDK):**
```python
from azure.search.documents.indexes import SearchIndexClient
from azure.search.documents.indexes.models import (
    SearchIndex, SearchField, SearchFieldDataType,
    VectorSearch, HnswAlgorithmConfiguration, VectorSearchProfile,
    SimpleField, SearchableField
)

# Define fields
fields = [
    SimpleField(name="id", type=SearchFieldDataType.String, key=True),
    SearchableField(name="content", type=SearchFieldDataType.String),
    SearchField(
        name="content_vector",
        type=SearchFieldDataType.Collection(SearchFieldDataType.Single),
        searchable=True,
        vector_search_dimensions=1536,
        vector_search_profile_name="myHnswProfile"
    )
]

# Configure vector search
vector_search = VectorSearch(
    algorithms=[HnswAlgorithmConfiguration(name="myHnsw")],
    profiles=[VectorSearchProfile(name="myHnswProfile", algorithm_configuration_name="myHnsw")]
)

index = SearchIndex(name="my-rag-index", fields=fields, vector_search=vector_search)
index_client = SearchIndexClient(endpoint, credential)
index_client.create_index(index)
```

### STAGE 5 — RETRIEVE 🔍

**What it means:** At query time, embed the user's question and search for the most similar chunks.

**The retrieval pattern:**
```python
from azure.search.documents import SearchClient
from azure.core.credentials import AzureKeyCredential
import openai

# 1. Embed the query
query = "What is the refund policy?"
query_embedding = openai.embeddings.create(
    model="text-embedding-3-small",
    input=query
).data[0].embedding

# 2. Search the index
search_client = SearchClient(endpoint, index_name, credential)
results = search_client.search(
    search_text=query,           # for keyword component
    vector_queries=[{            # for vector component
        "kind": "vector",
        "vector": query_embedding,
        "k_nearest_neighbors": 5,
        "fields": "content_vector"
    }],
    query_type="semantic",       # enable semantic ranker
    semantic_configuration_name="my-semantic-config",
    top=5
)

# 3. Collect retrieved chunks
context = "\n".join([r["content"] for r in results])
```

**Top-K parameter:** How many chunks to retrieve. Typically 3-10. More = more context (good) but more tokens (expensive) and more noise (bad). **k=5 is the exam default**.

### STAGE 6 — AUGMENT + GENERATE 💬

**What it means:** Build a prompt that includes the retrieved context, then call the LLM.

**The standard RAG prompt template:**
```
System: You are a helpful assistant. Answer questions ONLY using the provided context.
If the answer is not in the context, say "I don't know."

Context:
{retrieved_chunks}

User Question: {user_query}

Answer:
```

**⚠️ EXAM TRAP:** "What should the system prompt say to prevent hallucination?"
→ Instruct the model to answer ONLY from the provided context and to say "I don't know" if the answer isn't there.

### EVALUATING RAG — The 4 Key Metrics

Microsoft Foundry has **built-in RAG evaluators**. Know these:

| Metric | What it measures | Input required |
|--------|-----------------|----------------|
| **Groundedness** | Does the answer only use info from the retrieved context? (no hallucination) | answer + context |
| **Relevance** | Is the retrieved context actually relevant to the question? | question + context |
| **Coherence** | Is the answer well-structured and readable? | answer |
| **Fluency** | Is the answer grammatically correct? | answer |

**⚠️ EXAM TRAP:**
- **Groundedness** ≠ **Relevance**
  - Groundedness = answer grounded in context (anti-hallucination)
  - Relevance = context relevant to query (retrieval quality)
- Low groundedness → fix the **generation** prompt (tell LLM to stay grounded)
- Low relevance → fix the **retrieval** (chunking, embedding, search config)

**Running evaluations in Python (Microsoft Foundry SDK):**
```python
from azure.ai.evaluation import (
    GroundednessEvaluator,
    RelevanceEvaluator,
    CoherenceEvaluator
)

# Initialize evaluators
groundedness_eval = GroundednessEvaluator(model_config)
relevance_eval = RelevanceEvaluator(model_config)

# Evaluate
result = groundedness_eval(
    answer="The refund period is 30 days.",
    context="Returns and refunds: Items can be returned within 30 days of purchase."
)
print(result["groundedness"])  # Score 1-5
```

### RAG vs FINE-TUNING — The Decision Framework

This comparison appears constantly in the exam:

| Factor | RAG | Fine-Tuning |
|--------|-----|-------------|
| Data freshness | Real-time (re-index anytime) | Stale (must retrain) |
| Data volume needed | Any amount | Hundreds to thousands of examples |
| Hallucination risk | Lower (grounded in retrieved docs) | Higher (baked into weights) |
| Latency | Higher (search + LLM) | Lower (just LLM) |
| Cost | Per-query retrieval + generation | One-time training cost |
| Best for | Dynamic knowledge bases, Q&A | Style/format adaptation, specialized tasks |

**The exam rule of thumb:**
- Customer FAQ chatbot with a knowledge base that updates weekly → **RAG**
- LLM that needs to write in a specific company voice/format → **Fine-tuning**
- LLM that needs private knowledge AND a specific format → **RAG + Fine-tuning** (both)

## 🔧 HANDS-ON CHALLENGE (10 min)

**Task:** Build a minimal RAG pipeline in Python that:
1. Creates chunks from a small text (simulating document ingestion)
2. Generates embeddings using Azure OpenAI
3. Does a simple cosine similarity search (no Azure AI Search needed — just numpy)
4. Returns the top-3 most relevant chunks for a query

```python
import numpy as np
from openai import AzureOpenAI

client = AzureOpenAI(
    azure_endpoint="YOUR_ENDPOINT",
    api_key="YOUR_KEY",
    api_version="2024-02-01"
)

# Step 1: Your "documents"
documents = [
    "The refund policy allows returns within 30 days of purchase.",
    "Shipping takes 3-5 business days for standard delivery.",
    "Premium members get free shipping on all orders.",
    "To initiate a return, contact support@example.com.",
    "International shipping is available to 50 countries.",
]

# Step 2: Embed all documents
def embed(text):
    return client.embeddings.create(
        model="text-embedding-3-small",
        input=text
    ).data[0].embedding

doc_embeddings = [embed(doc) for doc in documents]

# Step 3: Search function
def search(query, top_k=3):
    query_emb = np.array(embed(query))
    doc_embs = np.array(doc_embeddings)
    
    # Cosine similarity
    similarities = np.dot(doc_embs, query_emb) / (
        np.linalg.norm(doc_embs, axis=1) * np.linalg.norm(query_emb)
    )
    
    top_indices = np.argsort(similarities)[::-1][:top_k]
    return [(documents[i], similarities[i]) for i in top_indices]

# Step 4: Test it
results = search("How do I return a product?")
for doc, score in results:
    print(f"Score: {score:.3f} | {doc}")
```

**Try:** Change the query to "How long does delivery take?" — observe which chunks score highest.

**Discussion:** Why might "free shipping for premium members" score higher than expected for the delivery query?
*(This is the semantic overlap problem — a real RAG challenge.)*

## 🎯 KEY TAKEAWAYS (memorize these)

1. **The 6 RAG stages:** Ingest → Chunk → Embed → Index → Retrieve → Generate. Each stage has failure modes the exam tests separately.

2. **Chunking rule:** Fixed-size with overlap is the default. Overlap prevents context loss at boundaries. Semantic chunking is best quality but most expensive.

3. **Embedding rule:** The SAME model must embed both documents AND queries. Mismatch = broken RAG.

4. **Search type rule:** Hybrid search (BM25 + vector) > pure vector for most real-world scenarios. HNSW is the default vector algorithm.

5. **Evaluation rules:**
   - Low Groundedness → fix the **system prompt** (generation problem)
   - Low Relevance → fix the **retrieval** (chunking/embedding/search problem)

6. **RAG vs Fine-tuning decision:**
   - Dynamic data that updates → RAG
   - Style/format adaptation → Fine-tuning
   - Both needs → RAG + Fine-tuning

7. **Portal terminology:** foundry.azure.com → Indexes (for data) + Prompt Flow (for pipelines) + Evaluation (for metrics). Know the navigation.
